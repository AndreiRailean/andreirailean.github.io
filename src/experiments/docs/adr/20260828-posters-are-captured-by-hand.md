# Posters are captured by hand and committed

## Context

`/experiments/` listed the pieces as text, which said nothing about what any of
them looks like — the one thing a programmed graphic is for. Each entry now
carries a still of its piece.

A still of a running canvas has to be produced by running it, so something has to
drive a browser. Where that happens is the decision.

It is also not a neutral capture. Dangler must settle first, because a frame
caught mid-relaxation shows a shape the scene never holds and nothing about the
image says so. Starry Night needs no warming up — its layers are seeded out of
phase, so frame one is already a sky — but a single shutter usually catches none
of the flaring its own summary promises, so it takes the brightest of twelve
tries. Knowing that is per-piece knowledge.

## Decision

`npm run posters` drives the pieces and writes a committed `poster.webp` beside
each one's code. A person runs it, when they judge that a piece looks different
enough to be worth re-photographing.

Each experiment owns a `poster.ts` recipe — which preset, what has to happen
before the shutter, how long to wait, how many frames to choose from.
`scripts/posters.ts` is generic and knows nothing about any piece; the shared
contract is types only, in `src/experiments/poster.ts`.

The slug filter (`npm run posters -- dangler`) exists because **no capture is
byte-reproducible**, for two different reasons. Starry Night takes no seed at
all. Dangler's landing preset is seeded, which fixes the arrangement, but its
wind is derived from the clock as well, so the shutter catches the same strands
at a different point in the same breeze. Neither difference is visible to a
person; both churn the file.

## Consequences

- The build stays browserless. `astro build` needs no Chromium and cannot fail
  because a headless capture was flaky.
- A poster can go stale. Nothing detects that a piece has changed its look and
  its still has not — the same class of thing as `updated` in the frontmatter,
  and kept current the same way.
- Committed binaries in a repo whose largest asset was a favicon. Astro
  optimises them to 6–11kB at display width; the script warns above 400kB.
- A third experiment does not get a poster for free. It writes a recipe, which
  is the part that was never going to be shared anyway.

## Considered options

- **Capture during the build.** Nothing binary in git, never stale. Rejected: it
  puts a headless browser on the deploy path for an image that changes maybe
  twice a year, makes the build much slower, and turns a flaky capture into a
  broken deploy.
- **A test that writes the poster.** No new tooling at all — the browser suite
  already opens each piece and takes stills. Rejected: `npm test` would start
  modifying tracked files, and `playwright.config.ts` is explicit that stills are
  scratch evidence for a human with nothing comparing them. An asset generator
  has the opposite contract.
- **Screenshot them by hand.** Zero machinery, best art direction, and honest
  that "it looks right now" is a human judgement. Rejected for reproducibility of
  _framing_ rather than of pixels: the viewport, the settling and the chrome
  suppression have to be identical between pieces and between captures, and a
  person doing that by hand will not.
